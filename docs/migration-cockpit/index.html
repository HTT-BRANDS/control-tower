1

Verify the App Service has a Managed Identity

No MI = no federation. This is the foundation.
To do ▶
What & why

OIDC federation works by trusting tokens minted by a known identity provider. In our case that provider is the App Service's system-assigned Managed Identity (MI). If the App Service doesn't have one bound, none of this can work.

Click-through path

Open the App Service → Settings → Identity → System assigned. Status should be On. Copy the Object (principal) ID into the MI principal ID field at the top of this page.

🚀 Open Identity blade in Azure Portal ↗

Or run via CLI
Copyaz webapp identity show \ --name {{site}} \ --resource-group {{rg}} \ --query '{principalId:principalId, tenantId:tenantId}' -o json
How you'll know it worked

The output shows a non-null principalId. If it's empty / null, click this to assign one:

Copyaz webapp identity assign \ --name {{site}} \ --resource-group {{rg}}
Tip: Paste the returned principalId into the MI principal ID field above — Step 2 needs it.
2

Add the federated credential to your app registration

Tells Entra ID "trust assertions minted by our App Service MI"
To do ▶
What & why

This is the actual federation hookup. We tell the management app reg: "a JWT issued by the home tenant, with this MI's principal ID as the subject, audience api://AzureADTokenExchange, is a valid credential." After this, the MI can authenticate AS the app reg — no secret needed.

Click-through path

Open the app reg → Certificates & secrets → Federated credentials → + Add credential. Pick scenario "Other issuer" (NOT the GitHub one — the federation source is the home tenant itself, since the MI lives there).

🚀 Open Certificates & Secrets for this app reg ↗

Exact field values (click any to copy)
Federation credential scenario Other issuer
Issuer URL https://login.microsoftonline.com/{{tenant}}/v2.0
Subject identifier {{mi}}
Audience api://AzureADTokenExchange
Name (your choice) app-service-mi-staging
Or run via CLI (faster)
CopyAPP_OBJECT_ID=$(az ad app show --id {{app}} --query id -o tsv) az ad app federated-credential create \ --id "$APP_OBJECT_ID" \ --parameters '{ "name": "app-service-mi-staging", "issuer": "https://login.microsoftonline.com/{{tenant}}/v2.0", "subject": "{{mi}}", "audiences": ["api://AzureADTokenExchange"] }'
How you'll know it worked

The portal toast says "Federated credential added". Or the CLI returns a JSON object with "name": "app-service-mi-staging". Refresh the Federated credentials list — your new entry shows up.

No async propagation lag: the credential is usable the moment the create call returns. You can move to Step 3 immediately.
3

Set the deploy flag in GitHub

A repository variable, not a secret. Tells the next deploy to flip to OIDC mode.
To do ▶
What & why

The deploy workflow reads vars.STAGING_USE_OIDC_FEDERATION to decide whether to push AZURE_AD_CLIENT_SECRET to App Service settings or DELETE it. Setting this variable is the single switch that turns the migration on.

It's a variable (not secret) on purpose — booleans aren't secrets, and we want the flag's value to appear in PR logs for auditability of the migration moment.

Click-through path

GitHub → repo → Settings → Secrets and variables → Actions → Variables tab → New repository variable.

🚀 Open repository variables in GitHub ↗

Exact values
Name STAGING_USE_OIDC_FEDERATION
Value true
Don't mix this up with Secrets: the value true should be a Variable, on the Variables tab, NOT the Secrets tab. If you put it under Secrets, the workflow won't see it (different YAML accessor: vars.* vs secrets.*).
How you'll know it worked

The Variables tab now shows a row: STAGING_USE_OIDC_FEDERATION = true.

4

Trigger a staging deploy

The workflow flips the runtime to OIDC mode + deletes the dormant secret.
To do ▶
What & why

The workflow reads the new repo variable. When it sees STAGING_USE_OIDC_FEDERATION=true, it:

• pushes USE_OIDC_FEDERATION=true into App Service settings
• deletes AZURE_AD_CLIENT_SECRET from App Service settings
• restarts the App Service so the new runtime config takes effect

Click-through path

🚀 Open deploy-staging.yml in GitHub Actions ↗

Click "Run workflow" → branch main → Run workflow. Or just push any commit to main.

What to look for in the workflow log

Open the run → expand the step "Configure Azure AD app settings (ct-wph + OIDC migration)". You're looking for these lines:

CopySetting Azure AD app settings on staging webapp (oidc_mode=true)... OIDC mode: removing AZURE_AD_CLIENT_SECRET from app settings (if present) ✅ Azure AD settings applied (OIDC mode — no client_secret in app settings)
If you see oidc_mode=false — the workflow didn't see your variable. Re-check Step 3: name must be exactly STAGING_USE_OIDC_FEDERATION, value exactly true (lowercase), on the Variables tab.
How you'll know it worked

The "Health check" / smoke-test step at the end of the workflow passes. The webapp is restarted with the new env. We verify in Step 5.

5

Verify /health/detailed reports OIDC

The runtime's self-report. This is the truth.
To do ▶
What & why

The post-ct-jxe credential probe runs against whichever auth path the runtime is configured for. It stamps auth_mode: "oidc" or "secret" on the result. If the migration worked, you'll see "oidc".

Open the endpoint

🚀 Open /health/detailed in browser ↗

Or curl from terminal
Copycurl -s https://{{site}}.azurewebsites.net/api/v1/health/detailed \ | jq '.checks.azure_configured'
Expected response (migration worked)
{ "status": "configured", "auth_mode": "oidc" }
If you see this instead

"auth_mode": "secret" → the runtime didn't pick up the flag. Restart the App Service:

Copyaz webapp restart --name {{site}} --resource-group {{rg}}

"status": "unauthenticated" with AADSTS700016 → the federated credential subject doesn't match. Re-check Step 2.

Any other AADSTS code → consult the rollback section of the runbook while you investigate.

6

Sign in end-to-end (incognito)

The /health probe doesn't exercise the OAuth callback. This step does.
To do ▶
What & why

The credential probe verifies the client_credentials flow that sync jobs use. The OAuth callback is a separate code path (auth-code grant with client assertion). Exercise it explicitly so you find auth-code-flow bugs before deleting the secret.

Steps

1. Open an incognito / private window (no cached session)
2. Open the staging site:

🚀 Open staging app ↗

3. Click "Sign in with Microsoft"
4. Complete Microsoft login
5. Verify you land on the dashboard with your user info populated

If login fails

Check App Service logs:

Copyaz webapp log tail --name {{site}} --resource-group {{rg}}

Look for:

• "OIDC federation failed during OAuth callback"
    → MI can't mint the assertion. Audience or subject is wrong. Re-check Step 2.
• "Azure AD token exchange failed (HTTP 401)"
    → Entra accepted our assertion but rejected the code. Likely user/group permissions — not OIDC.

7

Delete the dormant secret (24h waiting room)

After 24h green, kill it from 3 places. Then you're done.
To do ▶
Wait 24 hours after Step 5 first went green before doing this. The probe cache TTL is 5 minutes, so 24h gives ample time for any probe regression to surface. Don't skip the wait.
1. GitHub secret

🚀 Open repo secrets ↗

Find STAGING_AZURE_AD_CLIENT_SECRET → click the trash icon → confirm.

2. App registration client secret

Same place as Step 2 — Certificates & secrets. Find the active "Client secrets" entry → delete.

🚀 Open Certificates & Secrets ↗

3. Key Vault mirror (if any)
Copyaz keyvault secret list --vault-name <your-kv> --query "[?contains(name, 'client-secret')].name" -o tsv # Then for any matches: az keyvault secret delete --vault-name <your-kv> --name <secret-name>
How you'll know you're done

Re-curl /health/detailed after a webapp restart — you should still see "auth_mode": "oidc". The runtime never needed the secret, so deleting it changed nothing observable. That's the proof.

🎉 Touchdown. Zero runtime secrets.

Staging now runs without AZURE_AD_CLIENT_SECRET. Every Entra interaction — sync jobs, the OAuth callback, the health probe — uses a federated assertion minted on demand by the App Service Managed Identity. Nothing to rotate. Nothing to expire.
